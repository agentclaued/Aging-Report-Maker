Wal Mart Summary Workflow Documentation

This document explains how the current Wal Mart Summary FastAPI application works, using the live runtime structure in app/main.py, app/workflow.py, app/adapters/company_loader.py, and templates/index.html. It is written as an operational guide for business users, developers, and reviewers.

Runtime profile: wallmartsummary UI base: templates/index.html Main controller: app/main.py Transform engine: app/workflow.py Output folder: output/

1. Executive Summary

Business Purpose

The app turns inquiry sheets into normalized SQL tables, then runs matching and reporting queries so Wal Mart Summary teams can review invoice linkage, credit application, PO status, unapplied values, and deduction reporting.

Primary Runtime Pattern

Each workflow button on the template posts to a FastAPI endpoint. That endpoint validates or uploads files, prepares missing columns, writes master files into output/, refreshes SQL Server tables, and records a log/history message.

Design Scope

The runtime is intentionally locked to a single company. No company switching logic is exposed in the UI, and load_company_profile() now loads the active configuration from companies/wallmartsummary/.

5. Step-by-Step Workflow Documentation

Step 01

Inquiry Upload and Normalization

Buttons / Endpoint: for Wal Mart Summary, Process Wal Mart File uses /process/step-01. It reads the uploaded file locally, validates the required columns, copies the approved Wal Mart workbook template, calculates the report in Python, and downloads the workbook immediately. It does not create, refresh, query, or run a stored procedure against SQL Server.

Wal Mart calculation rules: required raw headers are Acct, Div, Name, Ref#, Date, Due Date, Order#, Current, 1-30 Days, 31-60 Days, 61-90 Days, Over 90 Days, Claim#, and Comment. Ref Type is optional: Python creates or refreshes it from the case-insensitive IN, DB, or CR match in Ref#. The processor preserves every uploaded column in WallMartSummary_Sheet, including extras. It converts Excel serial dates such as 44548 in Date or Due Date to real MM/DD/YYYY values. It refreshes/creates Total as Current + 1–30 + 31–60 + 61–90 + Over 90 Days; these six money columns display with a $ currency symbol in every output data sheet. The helper column is named PaidStatus and has no generic Paid value: it remains blank unless an explicit Unpaid or InvPaid rule applies. A blank Comment keeps every comment-based helper blank except InvYear. For IN rows, InvPaid requires a Comment that starts with one standalone Paid keyword, is not Paid Fully, and has no deduc wording; deduct anywhere sets Paid & Fully Deduct. Dispute applies to IN and DB rows. DB status groups by Acct, distinct Order#, and year of Date. Write-up Sent accepts Write Up, Writeup, Write-up, Write Up, or Write_up at the start, but excludes comments containing approval. The template's No Record Found column follows the No + Record comment rule.

Company selection: the Marketplace selector keeps the same UI. Wal Mart Summary, Amazon Accounts, and Regular Accounts process files without opening a database connection. Wal Mart includes only WC9085, WA9085, SA9200, and WM9263 in status totals, using the uploaded name value as each account label. Rows with blank or unsupported acct values are preserved in the master detail sheet, shown as a red warning in the log, and omitted from status totals.

Amazon account/type processing: every source sheet is read. The processor uses Acct and Ref Type, not source sheet names: IN creates <Acct>_Invoices, DB creates <Acct>_DBs, and CR creates <Acct>_CRs. It always creates these sheets for AM9285, AM9286, and ME9145.

Amazon status sheet positions: sheets 0, 1, and 2 are in this exact order: DB's Status, Invoice's Status, and CR's Status. DB and Invoice use their Amazon-only status rules; CR remains ready for its future rule.

Amazon Master Aging: sheet 3 is Master Aging. It contains every nonblank data row from every uploaded source sheet before any Amazon account or Ref Type filtering.

Amazon status formatting: DB's Status copies the approved DBs_Status format. Invoice's Status and CR's Status copy the approved Invoices_Status format. The Amazon template retains formatting only; it does not copy Walmart values.

Amazon download: Process Amazon File automatically downloads the completed workbook with the filename pattern Amazon Status Summary YYYY-MM-DD HH-MM-SS.xlsx.

Amazon busy state: the process button keeps the browser-native download response and displays Processing... until the server has finished sending it. A server completion status check replaces the fixed reset timeout.

Amazon DB status sample: DB's Status filters only Ref Type=DB rows, groups Acct, distinct Order#, and YEAR(Date), then writes the summed Total under the dynamic year headings. Write-up Sent sums Total where Comment contains MEMO case-insensitively. Dispute_Amount is not included in the Amazon DB status layout.

Amazon Invoice status: Invoice's Status filters Ref Type=IN, groups Acct and YEAR(Date), and sums Total into the dynamic year columns and Total Amount. Its final Paid @<latest YYYY> column uses the latest Date year only, groups Acct, Comment, and year, then sums Total where Comment contains Paid on, a payment-number phrase, and digits. Small spelling errors such as payemnt no are accepted.

Amazon CR status: CR's Status filters verified Ref Type=CR rows, the same rows written to <Acct>_CRs. It groups Acct and YEAR(Date), sums Total into dynamic year columns and Total Amount, and leaves Status as a - placeholder.

Amazon zero-total rule: do not render an account status section whose final Total Amount is 0.00. The rule is independent of account position and applies to every Amazon status summary as it is added.

Amazon account/type sheet rule: create an <Acct>_Invoices, <Acct>_DBs, or <Acct>_CRs worksheet only when filtered source rows exist. Empty account/type worksheets are omitted.

Amazon status formatting cleanup: after the final visible account section, the processor removes all unused template rows and formatting. Empty accounts leave no title, table, spacer, or formatting footprint.

Collapsed workflow tools: every workflow section below Full Report is placed inside Expand Workflow Tools, including runtime details, manual procedures and Proc Query, table export, preview, and configuration/health links.

Input: one inquiry file in .xlsx, .xls, or .csv format.

What the query/process is doing: the file is read into pandas, column names are normalized to SQL-safe names, WalMartSummary aliases are applied, required columns are validated, and helper fields are created before the dataset is written to SQL Server.

New columns generated:

  • Ndatee: derived from the order field using characters 6 to 12 as a date token.
  • pay_day: total of aging buckets current, col_1_30_days, col_31_60_days, col_61_90_days, and over_90_days.
  • Cclaim: normalized claim key; when claim starts with DB or CR, the last 6 characters are used.

Primary SQL table generated: step_01_inquiry_rows

Output file generated: output/STEP_01_NORMALIZED_INQUIRY.xlsx

Automatic follow-up: after the SQL upload succeeds, the app runs dbo.sp_WallMartSummary_db_and_inv_tabels, dbo.sp_WallMartSummary_gen_DBs_Status, and dbo.sp_WallMartSummary_Invoice_Status, builds LATEST_SQL_TABLES.xlsx, and returns it as the browser download.

Used for: all downstream CR/IN/DB splitting, invoice matching support, and date-based update logic.

Credit Applied Sheet

Button / Endpoint: Run step_07_crApplied → /process/step-07

What the query/process is doing: builds the credit-applied reporting sheet through SQL.

SQL table generated: step_07_Credit_Applied_Sheet

Export availability: use Build Latest Tables Workbook for the workbook export; the separate applied-sheet export was removed.

Used for: final review of how credits were applied to invoice activity.

9. Operational Notes

Duplicate File Notification

The app checks existing source file names in SQL history for Steps 01, 02, and 03. A duplicate is allowed to proceed and a top-right notification identifies it; no duplicate-resolution choice is required.

Auto-Run Toggles

Steps 01, 02, and 03 each have an auto-run checkbox. The preference is stored in browser local storage and submits the form immediately after file selection.

Busy State Protection

The page switches to a busy mode on submit so users cannot accidentally trigger duplicate clicks while SQL or file processing is still running.

Download Strategy

The template exposes download links for generated files and the latest-tables workbook export so users can validate transformed files and SQL output tables.

Step 07 Workbook Merge

The separate Step 07 applied-sheet export was removed; Build Latest Tables Workbook is the workbook export.

10. Recommended Business Reading of the Flow

In business terms, the workflow starts by cleaning and structuring raw inquiry data into SQL-safe tables. Once those base tables exist, the later SQL steps classify the records into matched groups, mismatch groups, unapplied groups, credit-applied groups, and summary groups. The template is therefore not just a file-upload page; it is a staged reconciliation console.

Best use: run Step 01 first, then PO status and match audit steps, then exception or credit reporting steps, then Step 07, and finally build and download the Latest Tables workbook.

Important caution: some buttons in Step 06 are marked as danger-zone actions in the template, which signals that they should be run only after the expected source tables have already been prepared.
